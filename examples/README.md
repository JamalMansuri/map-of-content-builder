# examples/

A complete, tiny, self-contained corpus you can lint in one command, offline, with
nothing installed but Python and PyYAML.

```bash
python scripts/lint_corpus.py \
  --corpus examples/demo-corpus \
  --profile profiles/default.profile.yaml
```

It reports **1 error and 1 warning**, both real, both planted on purpose. That single
run demonstrates the whole point of the tool: it mechanically checks that every quotation
on a generated page actually appears in the file that page cites.

---

## What is in here

```
│   ├── MAP.md                                          generated by build_spine.py

│   │   ├── service-design-order-intake.md
│   │   ├── incident-checkout-timeouts.md
│   │   ├── decision-blue-green-deploys.md
│   │   └── runbook-queue-backlog.md
│   ├── 01_sources/
│   │   ├── design_notes/normalized/records.jsonl       one record per source file
│   │   └── _spines/project_records.jsonl               the union of every bucket
│   ├── 03_workstreams/platform_reliability/
│   │   ├── current_brief.md                            human-owned, excluded from the lint
│   │   └── hold-window-inherits-incident-lag.md        the relationship page
│   └── 90_system/config/corpus.config.json
└── regenerate-demo.sh                                  optional rebuild
```

The subject is one small software project: a queue-backed order intake service, an
incident writeup about it, the deploy decision that came out of the incident, and the
on-call runbook. Four short documents, nothing to install, nothing to read for more than
five minutes.

The one page under `03_workstreams/` is a **relationship page**. It argues that the hold
window in the deploy decision was sized by a single lag figure the incident happened to
measure. It carries four provenance traces at the bottom:

```
<!-- trace: <record_id> | <ordinal> | <locator> | raw: "<verbatim span>" -->
```

Two of them are correct. Two are wrong, in the two different ways that matter.

## What the lint reports, and why

Real output, unedited:

```json
{
  "run_id": "20260803-1816",
  "corpus_id": "default",
  "mode": "audit",
  "pages": 1,
  "pages_gated_out": 1,
  "records": 4,
  "traces": 4,
  "traces_verified": 3,
  "inline_citations": 10,
  "errors": 1,
  "warnings": 1,
  "advisories": 0,
  "checks_skipped": {
    "NAME_LEAK": "profile declares no `path_is_sensitive` substrate root"
  },
  "machine_verified": "mechanical checks only; semantic checks are queued, not judged"
}
```

and the two findings:

```
TRACE_ABSENT   error    03_workstreams/platform_reliability/hold-window-inherits-incident-lag.md:55
  quoted snippet does not occur in the cited source (this means the QUOTATION could not
  be confirmed, not that the claim is false)
  source_id=design_notes:incident-checkout-timeouts.md · locator=H:contributing-factors
  raw="the dead-letter threshold of five attempts was too generous for an outage shaped like this one"
  hint=first 8 words occur at offset 830 (1× in source) -- likely a paraphrase

TRACE_LOCATION warning  03_workstreams/platform_reliability/hold-window-inherits-incident-lag.md:56
  snippet is in the cited source but not at locator 'H:context'
  source_id=design_notes:decision-blue-green-deploys.md · locator=H:context
  raw="The hold period is bounded by the worst consumer lag we have measured"
```

### The four traces, one at a time

| # | Result | Tier | Why |
|---|---|---|---|
| 1 | VERIFIED | `exact` | The span occurs byte-for-byte under `## How it failed` in the incident writeup, which is the section the locator names. Silent — a passing trace produces no finding. |
| 2 | VERIFIED | `exact` | Same, for `## Decision` in the decision record. |
| 3 | **ERROR** — `TRACE_ABSENT` | none | This is the interesting one. The source says the threshold "was too high for an outage of this shape". The page quotes it as "too generous for an outage shaped like this one". The **claim is true**; the quotation marks are not. That is provenance drift, and it is the failure mode this tool exists to catch. |
| 4 | **WARNING** — `TRACE_LOCATION` | `exact` | The span is genuinely in the decision record, verbatim, but it lives under `## Consequences` and the trace cites `H:context`. The quote is real; the address is wrong. |

### Why 3 and 4 are not the same severity

A snippet that is **absent from the cited source** is an error: the quotation cannot be
confirmed at all. A snippet that is **present but not where the page says** is a warning:
the evidence exists, the citation is imprecise. Collapsing the two into one severity is
the fastest way to make a report useless — a reader who sees a wall of same-coloured
findings mutes all of them, including the ones that were worth acting on.

Both severities are declared in `profiles/default.profile.yaml`, not in any `.py`. Lower
them there if you disagree; you cannot raise them above the ceiling the code declares.

### On finding 3, stated carefully

`TRACE_ABSENT` says *this quotation could not be confirmed*. It does not say *this claim
is false*, and the demo is built to make that distinction concrete: trace 3 paraphrases a
sentence that really is in the source and really does support the claim on the page.

This is not a hypothetical failure mode. On one real 39-page corpus of AI-drafted pages,
**116 of 448 quoted snippets did not appear verbatim in the source each was cited to** —
roughly a quarter. Hand-checking a sample of them showed the dominant cause was exactly
what trace 3 does: a close paraphrase presented inside quotation marks, with a claim that
was substantively correct underneath it. A model asked for a claim *and* its supporting
quote will paraphrase unless something forces it not to. Verifying afterwards is what
forces it.

### What a passing trace does and does not prove

It proves the quoted string physically exists in the named file right now, and that the
citation resolves to a real path. It does **not** prove the span supports the claim it is
attached to. If one model wrote both the claim and its trace, this converts an unbounded
risk into a bounded one. It does not eliminate it.

## Other things this run shows

- **`pages_gated_out: 1`.** `current_brief.md` is hand-written and carries
  `ai-generated: false`, so the profile's `discovery.gate_fields` excludes it. The
  exclusion is named in the report, never silent.
- **`NAME_LEAK` skipped, with a reason.** The demo declares no sensitive source roots, so
  there is nothing for that check to scan for. A check with no data to read reports itself
  as not run rather than passing vacuously.
- **Zero mutations.** The linter never edits a file it audits. With
  `report.queue_in_corpus: false` in the default profile it does not even add one; the
  report and the semantic queue land beside each other outside the corpus.
- **Exit code 0.** A full audit reports; it does not fail your build. Use `--gate` for
  write-time enforcement, which runs the provenance checks only and exits 1 on any error.
- **A `STALE` advisory may appear** if you run this long after the demo was authored. The
  pages are dated, and `temporal.staleness_days: 90` in the profile is the threshold.
  Advisory only; it never affects the error or warning counts.

## It works from anywhere

The `evidence_paths` in the shipped records are **relative to the corpus root**
(`sources/incident-checkout-timeouts.md`, not an absolute path from whoever built it).
The resolver anchors
relative evidence paths to the corpus root, so the demo produces identical results after
being copied to any directory, on any machine, run from any working directory. That was
verified by copying the whole repo elsewhere and re-running — same 1 error, 1 warning,
same line numbers.

If you build your own corpus and want it portable, write relative evidence paths too.
Absolute paths work, they just stop working on the next machine.

## Point it at your own folder

1. **Scaffold a corpus.** Write a corpus config naming your source folder, then:

   ```bash
   python scripts/scaffold_corpus.py --config my-corpus.config.json --output-root ~/corpora
   ```

   Your source root must not sit inside the corpus root — otherwise the corpus ingests
   its own output on the second run, and the scaffolder refuses. (The demo breaks this
   rule deliberately, to stay self-contained; see `PROJECT_HUB.md`.)

2. **Ingest.** One record per source file, with a content hash and a resolvable evidence
   path:

   ```bash
   python scripts/build_records.py --root ~/corpora/my-corpus
   python scripts/build_spine.py   --root ~/corpora/my-corpus
   ```

   `build_records.py` will not invent a one-sentence summary for a source that does not
   declare one. It stops, writes a queue, and waits. Every source note in this demo
   declares `summary:` in its frontmatter, which is why the demo build never stops there.

3. **Write pages**, in `03_workstreams/<name>/`, from the relationship template. Copy
   quoted spans out of the open source file character-for-character. Do not retype them
   from memory, do not tidy the punctuation, do not merge two spans with an ellipsis.

4. **Lint**, with the shipped profile or your own copy of it:

   ```bash
   python scripts/lint_corpus.py --corpus ~/corpora/my-corpus \
                                 --profile profiles/default.profile.yaml
   ```

   If the vocabulary does not fit your corpus, copy the profile and edit it — the type
   names, required fields, status values, token bounds, severities and thresholds all
   live there. Editing the code is the wrong move; that is the whole design.

   `python scripts/lint_corpus.py --list-checks` prints the full catalogue.

## Rebuilding the demo

Optional. The committed corpus is already the output of this:

```bash
examples/regenerate-demo.sh
```

It re-derives `records.jsonl`, the spine and `MAP.md` from `demo-corpus/sources/` using
the real scripts, then rewrites the evidence paths to be corpus-relative so the result
stays portable. It never touches the source notes, the hub, the brief, or the
relationship page — those are authored, not derived.

One field will differ after a fresh clone: `source_updated_at` is taken from each file's
modification time. Nothing the linter checks reads it.
